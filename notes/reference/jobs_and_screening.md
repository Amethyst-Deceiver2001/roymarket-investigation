## Status board (added 2026-10-02 at user direction)

`python3 scripts/status_board.py` says, per entity, person, product and Telegram channel, what the record lacks: a register extract or БФО never pulled, a pull or sanctions screen past its threshold (ЕГРЮЛ 45 days; ГУР and Aleph 30; OpenSanctions 90, its quota), open questions, unreviewed sanctions-type screening hits, unsourced history, and **developments not yet in the record**. The last come from the weekly scan's `developments.json` in `data/watch/` (falling back to the cloud folder `/mnt/project-files/watch/` until migrated; `--developments` / `--scan-state` override). An item stays open until someone sets `status: recorded|dismissed` with a `note` there; archiving the post does not close it. The board is viewed locally, not as an artifact (the artifact was deleted 05.10.2026; republishing cost about 200k tokens because the page embeds 550 KB of data): run `python3 exhibits/serve_status_board.py` in its own terminal and reload http://127.0.0.1:8765/, which rebuilds the page from the registry on every load (127.0.0.1 only: the page carries ИНН and open questions); `exhibits/build_status_board.py` writes the same page to a gitignored file, and it never goes in `docs/`. Besides the per-record flags, since 05.10.2026 the page opens with a **System checks** strip (newest post in the local scrape, last daily round, last weekly scan, last registry commit, sanctions claims read against an official list, ties without a document, people with a DOB and no per-field source, handover recipients resolved to a unit, queued media not yet looked at, open developments) and three flags: `sanction_unread` (a sanctions[] claim resting on an aggregator match, no official entry read), `tie_not_documented` (cbst_tie graded t-open or press) and `identity_unproven` (a sanctions entry that belongs to a same-name person). Every flag is a stated test in the script; a flag is a work item, not a finding. **Priority (23.10.2026):** rows are ordered by `priority_key` in the script: sanctions evidence waiting for a read first, then a ЦБСТ-tied organisation no Western list names, then listed records; within a level, hops from ЦБСТ (undirected BFS), then edges, then flag work; unflagged records last. Each row says why on the page; `python3 scripts/status_board.py --next 20` prints the list. Fixtures: `tests/test_status_board.py`. **Daily pulls (user, 02.10.2026: "missing pulls should trigger actual pulls"):** `--pull-queue` prints capped commands (8 per registry per day, top tiers first) for flagged ЕГРЮЛ/ЕГРИП and БФО gaps, then capped sanctions re-screens (OpenSanctions 4 a day, people and never-screened first, within its 150-record monthly quota; ГУР and Aleph 8 each, via each script's `--only`; added at user direction 02.10.2026), plus the local ingest steps. A screen hit is a lead to read, like any screening output. Registry sites are unreachable from the cloud, so the queue runs on the user's Mac as a scheduled job (see Coordination above). This capped daily batch is the user's standing go-ahead and stays within the "handful" the pull scripts allow; a full-roster sweep is still handed over as a command. A pulled document is read before any fact from it enters the registry. The queue's ingest chain ends with `build_relationship_graph.py` before `check_registry.py`; after it, `first_reading.py export --push --local-dir data/sources/_inbox` and `read` give the worksheet the same day. **`python3 scripts/daily_mac.py`** (user, 02.10.2026) runs that whole round in one go: queue, pulls, ingest, export, read, and the board's new-or-cleared flags, with a report in `data/watch/daily/<date>.md` (`--dry-run` for the plan, `--skip-pulls`). The scheduled job adds `--publish` (03.10.2026): start from the latest main, then commit and push the mechanical outputs; it refuses when the tree was dirty or a `corrections_*.json` changed. It applies no fact. A БФО filing already on disk but not yet in `financials[]` is flagged `bfo_unread` (a reading task) rather than queued again, and records with an older filing on disk queue after records never pulled. Anything under a `_` or `.` name in `data/sources/` (`_daily/`, `_inbox/`, run logs, `.first_reading_exported.json`) is a working file: `inventory_sources.py` and `scan_sources.py` skip it, so it never becomes a source.

## Same crawling-jobs discipline as wb_watch

Inline reconnaissance (single post lookups, one-off WebFetch/curl checks,
EGRUL/БФО document reads) is fine to run directly. Anything that does real
work at scale against a live third-party service must be handed to the user
as an exact command to run themselves, never run in the background — this
applies to `scripts/tg_scan.py` here (see above) and to EGRUL/БФО pulls,
which are the user's own manual downloads due to daily rate limits.
`scripts/mine_leads.py` is NOT covered by this — it's local processing over
already-scraped data, no live network call, fine to run directly/repeatedly.

**Sanctions watch (added 2026-10-02 at user direction; scheduled run retired 22.10.2026, user).** The GitHub Actions workflow is deleted: it could not start without Actions minutes (the last two scheduled runs, 12.10 and 19.10, failed at job start on billing) and the user chose to retire it rather than fund it. The script, its tests and the gap/citations scripts stay and can be run by hand where the list hosts are reachable. The `watch/sanctions` branch is kept as a frozen snapshot of 05.10.2026; anything built from it (the gap table, citations, status board) is as of that date, and EU/US/UK/CH status is not refreshed. The paragraph below describes how it worked while live. `scripts/sanctions_watch.py` downloads the official US (OFAC SDN), EU (FSF consolidated), Swiss (SECO) and UK (FCDO) lists, one request each, and reports every entry that carries a registry ИНН or ОГРН: new and gone since the last run, listed but missing from the record's `sanctions[]`, and claimed in `sanctions[]` with no identifier match. Names alone never count as a hit. It ran weekly in GitHub Actions (workflow now deleted), because the cloud sessions' network policy blocks those hosts. State lived on the `watch/sanctions` branch, never on main, and an issue opens when something changes. A hit is a work item: read the entry on the official list and record it in `sanctions[]` by hand, citing the list entry. Fixtures: `tests/test_sanctions_watch.py`. Each run also rebuilds the sanctions-gap table (`scripts/sanctions_gap.py`: ЦБСТ-tied organisations by regime, revenue with its basis) and the citations worksheet (`scripts/sanctions_citations.py`: official entries for claims sourced only to OpenSanctions), saves both on `watch/sanctions`, and puts week-on-week status changes in the issue. `exhibits/sanctions_gap.*` and `exhibits/sanctions_citations.md` are snapshots of 02.10.2026; the branch holds the current ones.

**Evidence packets and exports (added 2026-10-02).** `python3 exhibits/build_evidence_packet.py <slug>` (or `--top N` for the largest ЦБСТ-tied companies with no Western list match) writes an internal draft packet to `notes/packets/<slug>.md`: identifiers, sanctions status, owners and directors, accounts, the ЦБСТ tie, products and claims, a fact-only draft statement of reasons and a numbered exhibit list. It stays a DRAFT until a person has checked every line against its exhibits; `--external` drops internal ids. `python3 scripts/export_data.py` writes `exports/` (FollowTheMoney JSON lines and CSVs, graph scope, no notes or contact details; `--no-pii`). Neither is published; sending either outside the project needs the user's go-ahead. `notes/methodology_draft.md` is the methodology page draft, with its open gaps listed at the end.

**`scripts/egrul_batch_pull.py`** (added 2026-08-22) is the same discipline
applied to a *scripted* EGRUL job, not just the manual PDF-download case:
it hits egrul.nalog.ru's open (no-captcha) lookup API in a loop across every
registry entity with an ИНН, to give the whole roster one synchronized
baseline snapshot date instead of scattered pull dates. Tested inline on a
handful of entities first (ordinary reconnaissance, fine to do directly),
but the full-roster batch was handed to the user as an exact command — a
systematic loop of 100+ automated calls is exactly the "real work at scale"
case this policy exists for, even against an unauthenticated open API.

**Per-script detail** (`egrul_batch_pull`, `tg_media_pull`, `zakupki_batch_pull` incl. the `zakupki_review` field rule, `tg_scan_users`, `screen_egrip_ip`, the ФНС «Прозрачный бизнес» screeners) and the **parser lessons** (sample before a full run, all-null is a parser signal, БФО non-profit `funds_*` never presented as revenue, filer read from the filename) are in `notes/reference/script_notes.md` — read it before running or changing any of them. Rules that stay here:

- Live network jobs at scale (`tg_scan.py`, `tg_scan_users.py`, batch EGRUL/zakupki/ЕГРИП/ФНС sweeps) are handed to the user as an exact command, never run or backgrounded. Single lookups are fine inline. Two standing exceptions, both capped (user, 02.10.2026): the daily `status_board.py --pull-queue` batch, (the weekly `sanctions_watch.py` run in GitHub Actions is retired). Who runs which upkeep job, and where, is the table in `notes/rebuild_plan.md` §D; prefer those tools over hand-built lookups for the same work.
- After `tg_media_pull.py fetch`: run `inventory_sources.py` → `extract_registry.py` for real sNNNN ids, and copy the image into `docs/images/` or the HTML profile will not show it.
- Record a closed zakupki triage in the structured `zakupki_review` field (`{as_of, outcome: wired|partial|closed, note}`), not only in prose; trust `zakupki_coverage.py --gaps-only` over your own file counts.
- Any local job over ~100 files or ~2 minutes (user, 04.10.2026: background it, no handoff): say so up front, run it in the background with a monitor, and report when it ends. Handing the user a command is for live third-party sweeps only (see the first bullet). Run `tests/test_zakupki_parser.py` / `tests/test_bfo_parser.py` after touching those parsers.
- An all-null result for one entity or one field across the corpus is a parser bug until proven otherwise. Non-profit `funds_*` figures are never revenue.
- **Public snapshots of cited pages (added 2026-10-02):** `scripts/archive_sources.py` gives every Telegram post and web page a registry record cites a Wayback Machine capture, recorded with its date and the SHA-256 of the archived bytes in `data/registry/source_archives.json` (keyed by URL, listing its source ids; tier 1 = cited posts and pages, 2 = cited zakupki/fips pages, 3 = uncited). `plan`/`local`/`report` are local; `lookup`/`save`/`run` are network jobs; the batch used to run in GitHub Actions and is abandoned (24.10.2026; run it by hand) (`.github/workflows/wayback.yml`, commits the JSON to main; set repo secrets `WAYBACK_S3_ACCESS`/`WAYBACK_S3_SECRET` for the faster keyed endpoint). The cloud network blocks web.archive.org. A capture is public; it does not record who asked. **Telegram posts are not archived on the Wayback Machine (user, 03.10.2026: "we're not web archiving telegram posts").** `archive_sources.py` skips every Telegram URL unless `--include-telegram` is passed; the nightly job does not pass it. Telegram posts are preserved by our own record (text and raw fields from `data/roymarket.db`), the RFC 3161 stamps below, and a per-cited-post evidence bundle with the media (see `scripts/media_triage.py`). The earlier per-channel index lookup, preview-page saves and embed-view logic stay in the script behind the flag and are not used; the 442 existing captures stay in `source_archives.json` as they were.
- **Timestamped source fingerprints (added 2026-10-03 at user direction):** `python3 scripts/timestamp_sources.py build && … stamp` hashes every file in `data/sources/` into `data/registry/timestamps/<date>/manifest.sha256` (`shasum -a 256 -c` format) and has the list signed by two RFC 3161 authorities (FreeTSA, DigiCert); `verify` re-checks files and signatures. It proves we held exactly these bytes by that time; it cannot prove Telegram served them. Commit the folder. A file whose bytes differ from its `sources.json` hash goes in `changed_since_catalogued.tsv`: a work item to explain, never re-hashed silently. Run it after a batch of new sources. **Never overwrite a file in `data/sources/`:** every script writes there through `source_files.write_new()`, which leaves an existing file alone and writes a changed re-fetch as `<name>-r2.<ext>` (fixtures: `tests/test_source_files.py`). The first run found 121 files rewritten in place (trademark JSON re-parsed on 25.08, same-day re-fetches, appended notes); their catalogued hashes were brought in line with the stamped bytes on 03.10.2026, and the old hashes stay in that run's tsv. Hand-made notes and transcripts in `data/sources/` are also fixed once catalogued: add a new dated file rather than editing one.
- **First reading of daily pulls (added 2026-10-02 at user direction; moved fully onto the Mac 05.10.2026, issue #30).** After the pull queue, the Mac runs `python3 scripts/first_reading.py export --local-dir data/sources/_inbox`: the text of each new ЕГРЮЛ/ЕГРИП/БФО file (not the PDF) is written locally, then `first_reading.py read` sets the registry's values beside the document's own lines in a worksheet. The result is a note for the user; nothing enters the registry until a human has read the document. The export no longer pushes to `pull-inbox` — that branch and the cloud routine that read it are retired, since the cloud's read was a second pass over the same text main re-reads anyway before applying anything.

**Python 3.11 parity (user, 08.10.2026).** CI (now abandoned) ran Python 3.11 and the Mac a newer one, so 3.12-only syntax (a backslash or a reused quote inside an f-string expression) passed locally and turned 14 pushes red.
