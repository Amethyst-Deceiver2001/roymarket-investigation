Product Icon Set

Right now every products[] node on the graph renders as the same plain square — a strike drone, a jammer, and a battery are visually identical. This proposes 17 monoline category pictograms plus an explicit 18th unclassified glyph, grounded in the actual spread of the registry's 487 product entries, so a reader can tell a kamikaze quad from a counter-drone detector from a spare battery without opening the detail panel — and can tell "not yet classifiable" from "quietly forced into the wrong bucket."

Design precedent: MIL-STD-2525/APP-6 military symbology keeps a symbol's frame (affiliation) and its interior icon (unit type) orthogonal — an operator learns the icon vocabulary once and reuses it regardless of frame. Node kind already owns the frame here (square = product, unchanged); these icons only fill the interior, the same way tier owns color and the hub badge's fill-pattern owns offensive/defensive/dual — a fourth independent channel, not a competing one. Stroke weight and grid are held constant across all 18 per ISO 7000's consistency guidance for equipment-symbol families, so the set reads as one vocabulary rather than 18 unrelated drawings.

01 Classification rule — no longer implicit

2026-09-14 revision: the original mockup assigned categories by eyeballing text with no stated fallback — concretely, all 27 EW-jammer hits in the first pass shared one undifferentiated count despite three separate jammer icons being shown, with no rule for which one a matched product should get. Fixed with a real, checked-in classifier (scripts/classify_product_icon.py), not just prose:

Tier 1 — structured, where it exists

  1. If a product carries a type_bvs field (wired 2026-09-14 from rk.2035.university's own product sub-catalog, source s1169, for 6 entities so far), map it directly — only 4 distinct values exist in that source, all airframe types, so this only ever resolves the 4 airframe categories. A structured airframe type still gets overridden to FPV / kamikaze strike if the text itself uses strike language — type_bvs says nothing about intent, only shape.

Tier 2 — keyword, with an explicit default

  1. Everything else (the large majority of the corpus) falls to keyword matching against name_ru + description — bilingual: Russian and English terms both, after the original English-only-description gap (gk-logos's real jammers were falling to "unclassified" because their descriptions read "Omnidirectional vehicle-mounted EW jammer" — no Russian trigger word at all) was found and fixed. A second pass (same day, triggered by manually triaging the unclassified bucket rather than trusting the count) found two more bilingual gaps — Cyrillic "ФПВ" wasn't recognized as equivalent to Latin "FPV", and English "kamikaze" wasn't recognized alongside "камикадзе" — plus a semantic inversion: "maintain link when jammed" (a strike drone describing its own EW resistance) was matching the same bare substring as "jammer", misclassifying an airframe as its own countermeasure. All three fixed with tighter, not looser, patterns.
  2. A third pass found the detector count was conflating three unrelated device classes — the same "one undifferentiated bucket" problem the jammer mount-rule fixed, but one level deeper. "детектор"/"пеленгатор"/"detector" alone also matches landmine detectors and walkthrough metal-detector arches (ooo-opkb-eksplomet's АЛЬФАМАРИН/ARENA line — airport-security-style personnel screening, not drone-related at all) and a manned-aviation radio direction-finder (ao-pk-azimut's DF 2000). Both entities are already known to sit outside this taxonomy's industry (see §03) — the bug was letting one shared English gloss word pull their products into a UAV category anyway. An explicit exclusion guard removes 8 false hits without loosening the real detector patterns.
  3. EW jammer mount-type sub-rule, stated explicitly: переносн/portable → portable icon; стационарн/dome/fixed → stationary icon; автомобил/vehicle-mounted/omnidirectional → vehicle icon; no match on mount language → vehicle-mounted (the modal case in the original count, now a stated default instead of a silent one).
  4. Two categories added 2026-09-14 after triaging the unclassified bucket by hand rather than treating a large count as self-explanatory: Electronics / compute module and Navigation / GNSS module — a real slice of this registry isn't complete-UAV manufacturers at all but B2B component suppliers feeding other manufacturers' airframes (npts-elvis's ~30 chips/SoCs/processor modules; ooo-4gnss/ooo-orient-sistems's ~15 GNSS receiver boards), previously indistinguishable in the unclassified count from genuinely unrelated-industry noise. Motor / propeller / part was broadened to Motor / propeller / rotor blade (also now covers starter-generators) rather than spin up a 19th icon for a term with zero literal hits in the corpus as of this writing.
  5. No category matches at all → the 18th "unclassified" glyph, not a forced nearest-neighbor guess. On the live corpus this is still the single largest bucket (190 of 487) — mostly one entity, ao-pk-azimut (51 products: air-traffic-control avionics, biometric scanners, servers), whose entire product line is a different industry this taxonomy was never meant to cover. That's the fallback working as intended, not a coverage failure — see §03 for the full triage of what's left.

Live distribution as of this revision: FPV/strike 51 · multirotor/cargo 33 · electronics/compute 30 · fixed-wing/VTOL 25 · detector/counter-UAS 26 · jammer-vehicle 40 · battery 16 · nav/GNSS 15 · antenna 7 · helicopter 7 · motor/part/rotor 5 · jammer-stationary 4 · jammer-portable 5 · video link 3 · repeater 2 · ground control station 1 · munition 1 · unclassified 190. 25 products resolved via the structured tier, 246 via keyword (6 via the explicit generic-UAV-term default, documented above), 190 unclassified — run python3 scripts/classify_product_icon.py for the live count any time the registry changes.

Fiber-optic-guided (modifier tag)
Small coil badge overlaid on the corner of a drone icon (e.g. «Провод-15», ВОЛС cable spools) rather than its own category — it's a guidance-method variant of an existing airframe, not a different kind of object.

Why 17+1 categories, not fewer: a strike quad, a cargo quad, and a fixed-wing craft already collapse to one "product" square today — the registry treats them as meaningfully different (different products[] language, different evidentiary weight for an offensive/defensive read). The two newest categories exist for the same reason: a semiconductor die and a GNSS receiver board are both "components," but they're different objects to a reader, and folding either into an airframe icon would misrepresent a B2B parts supplier as a drone maker. Fewer categories would just move the ambiguity from the whole graph down to this icon set. Why not more: a category with 1-2 hits (video/control link, munition) folds into its nearest neighbor's icon family rather than getting its own glyph nobody will learn to recognize — this is also why rotor blades didn't get a 19th icon: zero products in the corpus are literally described as a blade, so the existing motor/part icon absorbed the label instead of a glyph with nothing behind it. Why the 18th matters: the first pass had no explicit "doesn't fit" state, which is indistinguishable from a wrong guess to a reader — 200 real products in this corpus are legitimately outside UAV hardware entirely (server boards, biometric scanners, weather sensors, unmanned ground robots), and the honest move is to show that, not force them into "battery" because it's the closest available shape.

03 What's still unclassified, and why

The 190 remaining products split into four real categories, not one undifferentiated pile:

  1. Different industry entirely (~160) — ao-pk-azimut's ATC navaids/biometric scanners/servers (51, this entity's whole product line); npts-elvis's IP security cameras (11 — a stationary-CCTV line, not a UAV EO/IR payload, checked and ruled out rather than assumed); ooo-kravt's powerbanks/EV chargers/3D printer (14); npp-radar-mms's weather/hydrology sensors, pulled in by the same GISP catalog sweep as their actual UAVs (14); ooo-opkb-eksplomet's landmine/walkthrough-metal-detector security-screening line (8, see §01's third pass); assorted singletons (a dog body-armor line, a youth STEM program, a tethered aerostat).
  2. Real UAV/EW product, but blank source text (~40) — a data gap, not a classifier bug. ao-stratim (Русак-С/Голубь/Тювик), ao-tekhnodron (Скворец), and ooo-skb-piranya (Пиранья 15/"20") each carry a duplicate stub entry with empty description sitting beside a sibling entry that has real GUR/catalog text and classifies correctly. ooo-npo-kilovatt-shestopalov's remaining К-*/ТП-* model codes (22) likely belong to the same jammer/case line already confirmed elsewhere in this entity's catalog, but have no pulled description to confirm from.
  3. Real product, no matching category (~10) — a scope decision, not a bug. ao-ploshchad's autopilot/machine-vision modules and targeting software have no "avionics/software" category yet; npp-radar-mms's radar-seeker heads for Kalibr/Kh-35/Kh-59 munitions sit between munition and detector without fitting either cleanly.
  4. A different object class, watching for more evidence (4) — ooo-gagaring's tracked ground robots («Молот», «Молекула», «Атом») are genuinely not aircraft; forcing a UGV into any airframe icon would misrepresent it. Left unclassified rather than reused/force-fit for now — one entity, four products isn't yet enough signal to justify an 18th pictogram nobody else's catalog would populate. Revisit if a second UGV maker turns up in the registry.
